# 代码库死文件审计（带闭环验证）

判断"这个文件没人用"不能靠肉眼，也不能只靠静态分析。本文给出的三步闭环能给出**可被证伪**的结论。

## 核心思想：负向对照

只做"删掉候选 → 构建还通过"是不够的。如果分析器太宽松（把所有东西都判成"被引用"），
那么"没有死代码"这个结论也一样成立，却毫无价值 —— 你只是没发现而已。

**所以必须加一步负向对照：删掉一个已知被大量引用的文件，构建必须失败。**
如果这一步不失败，本次审计的全部结论作废，先去修分析器。

## 三步闭环

| 步骤 | 做法 | 期望 |
| --- | --- | --- |
| ① 静态分析 | 从入口做引用可达性分析 | 产出候选集 |
| ② 正向验证 | 副本中删候选 → 重跑构建 | **必须仍通过** |
| ③ 负向对照 | 副本中删已知被引用的文件 → 重跑构建 | **必须失败** |

**全程在副本中操作。** 复制项目时排除构建产物：

```bash
mkdir -p $AU/baseline
cd <project> && tar czf - --exclude=backend/target --exclude=frontend/node_modules . \
  | tar xzf - -C $AU/baseline
```

## 根节点必须覆盖的"非 import"机制

静态分析最大的漏判来源是"靠约定生效"的文件。逐项确认：

| 机制 | 处理 |
| --- | --- |
| Spring 反射 | 带 `@RestController`/`@Service`/`@Component`/`@Entity`/`@Mapper`/`@Configuration` 等注解的类**全部作根** |
| 程序入口 | `@SpringBootApplication` 标注类 |
| 测试类 | Surefire 命名约定 `*Test`/`*Tests`/`Test*`/`*IT`，**外加**含 `@Test` 方法的类 |
| Flyway/Liquibase 迁移 | 靠命名约定执行，**强制全部保留** |
| 前端 `.d.ts` | 由 `tsconfig include` 交给编译器加载，**必然不出现在引用图里，属必然误报**，要单独归类而不是报成孤立 |
| 前端动态导入 | 先 `grep -rn "import.meta.glob"` —— 用了 glob 自动注册，import 分析就不可靠 |
| MyBatis XML | 单独搜 mapper XML 里的类名 |
| 配置文件引用 | `application*.yml`、`META-INF/` 里提到的类 |

**踩过的坑**：把 `vite-env.d.ts` 报成孤立文件。它声明 `ImportMetaEnv`，
删掉会让 `import.meta.env.VITE_*` 全部失去类型。任何 `.d.ts` 都不该出现在孤立清单里。

## Java 引用图的可靠做法

不要只解析 `import` —— 同包类不需要 import。三条边都要建：

1. 显式 `import x.y.Z`（含 `import x.y.*` 通配，展开为该包全部类）
2. **同包内的标识符引用**：扫描文件中所有 `[A-Z]\w+` 标识符，命中同包类名即建边
3. 源码中直接出现的全限定名

## 分类要分开：构建产物 ≠ 死代码

这两类的删除风险完全不是一个量级，报告里必须分档：

- **可再生**（`target/`、`node_modules/`、`dist/`、`*.class`、`*.log`）——删了能重新生成，风险≈0
- **死代码**（源码里无人引用的文件）——需要闭环验证
- **需人工判断**（运维脚本、文档、平台专用脚本）——"没人 import"是正常的，
  它们本来就是给人手工执行的，删不删取决于是否还在用
- **必须保留**（源码、构建配置、契约文件、环境变量文件）

很多时候真正占空间的**只有构建产物**，源码本身相当干净。先看数字再决定值不值得动。

## 基线是红的怎么办

老项目常见：main 编译通过，但测试编译或执行本来就是失败的。
这时不能用"测试全绿"当信号，改用**差分验证**：

1. 记录基线的失败集合（哪些文件、多少错误）
2. 删除候选后重跑
3. 判定标准改为：**main 编译仍通过，且失败集合不扩大**

同时把"基线是红的"本身作为**重要发现**报告出来 ——
它意味着项目当前没有回归保护，任何重构都在盲飞，
这件事的优先级通常高于清理文件。

## 归因：这个死文件是怎么来的

光说"这个文件没人用"用户往往不放心。**能追溯出它是哪次改动留下的，结论才可信。**

没有 Git 的项目里，用**成对的历史快照**做二分即可：

```bash
# 假设快照命名成对：*-before-<日期> / *-sync（改动前 / 改动后）
for t in *-before-*.tar.gz *-sync.tar.gz; do
  rm -rf /tmp/snap && mkdir -p /tmp/snap
  tar xzf "$t" -C /tmp/snap
  n=$(grep -rln "被查文件名" /tmp/snap --include=*.vue --include=*.ts | grep -v "被查文件自身" | wc -l)
  echo "$t 引用数=$n"
done
```

找到引用数从 N 掉到 0 的那一对，`diff` 那对里**引用该文件的宿主文件**，
就能看到"做了什么改动导致它被摘掉"。典型结果是：宿主被重构，只有该文件的
`import` 被删除，而文件本身忘了删。

### 区分「被替代」和「被撤销」

- 搜该文件的**独有类名 / 独有文案**（不要搜通用词）：
  - 只在自己文件里出现 → 功能整体**撤销**了
  - 出现在别处 → 功能被**搬迁**了，要去看新实现是否等价
- 再查**历史构建产物**（`dist/` 的 tar 包或镜像）里有没有它的独有标识：
  - 没有 → 说明在那个时间点它就已经没被编译进去，可佐证"当时已死"

### 附带收益

溯源经常顺带发现**同一次改动留下的其他尾巴**。
例如前端漏删组件的那次重构，后端可能同样留有"测试没跟着改"的问题。
把这类共性结论写进报告，比逐个文件罗列更有价值。

## 报告结构

1. 结论摘要（总占用 / 可回收 / 死文件数）
2. 审计方法（尤其说明负向对照为什么必要）
3. 可删清单（逐项附闭环验证结果）
4. 必须保留清单（按类别）
5. 需人工判断
6. **意外发现**（基线是红的、测试与源码脱节等）——这往往是最有价值的部分
7. 分析能力的边界（诚实声明静态分析看不到什么）
8. 建议动作（按优先级）

## 硬约束

- **绝不在生产目录上执行任何删除。** 所有验证在副本中进行。
- 报告结论只用于**指导**删除，实际删除必须单独取得用户确认。
- **必须先看磁盘余量**。如果磁盘空闲充裕、而可回收的只有几 MB，
  要直接告诉用户"这次清理不划算"，而不是照做。
- 一定要在报告里写清"静态分析看不到什么"，避免用户把"未发现引用"当成"一定安全"。
